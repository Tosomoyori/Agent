# 记忆系统：实现了什么，以及为什么没做更多

这份文档记录的是**刻意没做**的部分。作品集里最容易失分的不是「某个模块没写完」，
而是「写了个半成品还说不清楚为什么要它」。所以这里把边界划清楚：
哪些做了、哪些没做、没做的那些如果要做得怎么做。

---

## 已实现：工作记忆 + 持久化

代码在 [src/agentkit/memory/](../src/agentkit/memory/)。

| 机制 | 位置 | 解决什么 |
| --- | --- | --- |
| Token 预算裁剪 | [`working.py`](../src/agentkit/memory/working.py) `WorkingMemory.assemble` | 上下文撑爆之前主动丢弃早期对话 |
| 原子配对丢弃 | 同上 `_take_droppable_prefix` | 工具调用组整组一起丢，否则产生孤儿块 |
| 摘要压缩 | 同上 `summarizer` 钩子 | 被裁掉的信息用模型总结成一段保留下来 |
| 会话持久化 | [`store.py`](../src/agentkit/memory/store.py) | 跨进程记住对话 |
| 唯一装配入口 | [`manager.py`](../src/agentkit/memory/manager.py) | 「发给模型的消息长什么样」只有一处决定 |

### 为什么「原子配对丢弃」是这里最关键的一行代码

`tool_use` 和它的 `tool_result` 必须成对出现。裁剪历史时只丢掉一半，下一次请求
会直接失败（Anthropic 报错明确；OpenAI 系则表现为模型开始胡言乱语）。
所以 [`_take_droppable_prefix`](../src/agentkit/memory/working.py) 里，
当一组只能丢一半时，答案是**一半都不丢**。

这条不变量由 [`validate_conversation`](../src/agentkit/core/types.py) 在引擎每一轮
开头校验，两边是配套的。落盘前也会校验一次——取消或出错时消息序列可能残缺，
存下去会让下一轮一开场就违反不变量。

## 刻意没做：语义记忆、情节记忆、记忆整合

这三块是「记忆」这个方向上真正的深水区，也是很多 Agent 项目的宣传重点。没做的
理由不是没时间，而是**在我的场景里它们的收益不足以抵消引入的复杂度**——下面逐条说明。

### 事实标准长什么样

先说清楚业界现状（依据见文末）。记忆的**事实标准**是一条流水线：

```
抽取 (extract) → 整合 (consolidate) → 存储 (store) → 检索 (retrieve)
```

分层上普遍接受的划分是：

| 层 | 内容 | 典型实现 |
| --- | --- | --- |
| Working | 当前上下文窗口内的对话 | checkpointer / session（**本项目已实现**） |
| Episodic | 过去交互的摘要与示例 | 会话摘要 + 向量召回 |
| Semantic | 事实与偏好（用户画像、知识三元组） | 向量库 / 知识图谱 |
| Procedural | 行为规则 | 通常实现为**对 system prompt 的优化**，不是检索 |

**工业界落地最多的是「向量检索 + 会话摘要」**——mem0 的社区规模最大，
ChatGPT 的 memory 和 Microsoft Foundry 的托管实现走的都是这条路。
知识图谱（Zep / Graphiti 的时序事实建模）属于长尾，主要用在需要
「在某个时间点上什么为真」的法律、金融场景。

### 逐条说明为什么本项目不做

**语义记忆（事实抽取与检索）。** 它解决的问题是「跨会话记住用户是谁、偏好什么」。
本项目的会话持久化已经覆盖了「跨轮次记住同一会话内的信息」——实测演示里
第二轮的「我上一句问的是什么」答对了。再往上一层需要：
① 一个 embedding 模型（本地跑要拉权重，走 API 要额外成本）；
② 一个向量库依赖；
③ 一套抽取提示词；
④ 一套去重与冲突消解逻辑。
其中 ③④ 是真正的难点，而且**没有可接受的评测方式**——「记住了多少」很难
客观衡量，常见的做法是拿几个例子手动验证，那不算评测。

**情节记忆。** 在「向量检索 + 会话摘要」的架构里，它不是一个独立子系统，
就是 `type="episode"` 的存储条目。单独建模块是过度设计。

**记忆整合（consolidation）。** 它的成熟做法是：去重（嵌入相似度 + 实体重叠，
LLM 裁决）→ 矛盾消解（标记 `SUPERSEDED` 而不是删除）→ 异步 sweep。
每一步都需要嵌入模型和一个"睡眠"调度器。**在没有语义记忆的前提下，
整合没有对象可整合。**

**Procedural memory。** 它是 prompt 优化问题，和检索无关，放进「记忆系统」是
分类错误。本项目不做。

### 如果要做，路径是什么

按依赖顺序，三步，每步都能独立验证：

1. **加嵌入与向量检索**——为 `SessionStore` 增加一张 `facts` 表
   （`content` / `embedding` / `type` / `valid_from` / `superseded_by`），
   召回时用「向量相似度 + 关键词」混合检索。这一步做完就能演示
   「关掉记忆 vs 打开记忆」的评测对比。
2. **加抽取与冲突消解**——在被裁剪的历史上跑一次抽取，产出候选事实；
   对每条候选做 `ADD / UPDATE / DELETE / NOOP` 裁决；
   矛盾时标记旧条目的 `superseded_by` 而不是物理删除（保留可审计性）。
3. **加异步 sweep**——会话结束后用便宜模型跑一次整合，不阻塞主流程。

**验收方式**必须是仓库自带的评测（见 Phase 4）：比较开/关记忆时的任务成功率
和单位成本。没有数字的「记忆提升了效果」在面试里是负分。

## 一个仍需说明的取舍：token 估算是启发式的

[`estimate_tokens`](../src/agentkit/memory/working.py) 按字符数估算
（CJK 约 0.6 token/字，其余约 0.3 token/字符），没有用真正的 tokenizer。

理由与代价：

* DeepSeek 提供了一个 demo tokenizer，但它不是官方维护的库，打进依赖不划算；
* 也没有官方的 count_tokens 接口（Anthropic 和 Gemini 有，OpenAI 和 DeepSeek 没有）；
* 估算精度对**裁剪**够用——裁剪本来就该留安全余量，算多了只是少放几条历史；
* **计费一律以服务端返回的 `usage` 为准**，绝不用估算值。这是硬规则。

如果将来接入 Anthropic，可以走它的 `count_tokens` 接口拿到精确值——
那时 `estimate_tokens` 应该退化成「无接口可用时的兜底」而不是唯一实现。
