## 结果解读

**该结果说明基线稳定，不说明 agent 能力已饱和。**

22 个用例的考察点是：工具选择、递归遍历、干扰项排除、注释跳过、条件分支、
跨文件比对、引用链跳转。这些能力在 2026 年的前沿模型上已基本达到上限，
因此该套件对当前模型**不具区分度**——全部用例通过，无法区分模型的强弱。

作为**回归基线**，它有价值：任何改动之后跑一遍，可以立即发现能力退化。
作为**能力证明**，它不成立。

### 指标之间的关系

`pass^k ≤ TSR ≤ pass@k` 恒成立，报告同时给出三个：

- **TSR**：全部 110 次运行中通过的比例，反映平均表现；
- **pass@5**：至少成功一次的用例比例，反映能力上限；
- **pass^5**：五次全部成功的用例比例，反映**可靠性**。

本次三者均为 100%，说明在这批任务上不存在「时好时坏」的情况。
若出现 `pass@5` 高而 `pass^5` 低，则说明系统能完成任务但不稳定——
这是上线前最需要关注的信号，参考 τ-bench 的原始结论（retail 场景 pass^8 < 25%）。

### 提升区分度的方向

增加难度而非增加同类用例数量：多文件重构、需求存在歧义需要澄清、
长程规划（10 步以上）、以及**应当被拒绝执行的请求**。

## 判据设计约束

评测框架在使用中暴露出一类系统性错误，已固化为设计约束：

**`answer_not_contains` 检查的是措辞而非事实，会惩罚正确回答。**

两类具体表现：

| 类型 | 例 |
| --- | --- |
| 措辞误伤 | 判据禁止出现 `core.py`，而正确回答是「`core.py` 不以 `test_` 开头」 |
| 字面误伤 | 判据禁止出现 `E402`，而正确答案是 `E4021`（子串命中） |

由此确立两条规则：

1. **优先使用正面判据**（必须出现某个关键事实）。负面判据仅在所列的词
   **不可能**作为正确内容的一部分出现时才是安全的。
2. **判据难以结构化时，改问题本身，而不是改判据。** 例如不问「哪个文件的
   port 不一致」（需要解析散文），改问「那个不一致的 port 是多少」——
   答案唯一，判据为 `answer_contains: ["9090"]`。

第 2 条同时改善了评测的客观性：问题的答案越唯一，判据越不依赖语言模型的表达方式。

该约束也写在 `CheckSpec.contains` 的字段文档里（`src/agentkit/evaluation/case.py`），
位置在编写用例时会看到的地方。

## 三层测试的分工

项目中的三类验证回答不同的问题，不应当混为一谈：

| 层 | 命令 | 回答的问题 | 成本 |
| --- | --- | --- | --- |
| 单元测试 | `uv run pytest` | 各组件逻辑是否正确 | 0 |
| 评测（hermetic） | `agentkit eval ... --mode hermetic` | 评测框架自身是否正确 | 0 |
| 评测（live） | `agentkit eval ... --mode live` | agent 在真实任务上的表现 | API 费用 |

第二层与第一层的区别常被忽略：单元测试验证 `run_checks` 函数的行为，
hermetic 评测验证的是**整套用例 + 判据 + 工作区隔离**组合起来是否自洽。
判据写错的用例，单元测试全绿也发现不了。

**hermetic 模式的边界**：它验证框架自身的逻辑（工作区隔离、聚合算法、判据执行），
不验证判据的措辞是否合理。后者只有在真实模型给出解释性回答时才会暴露——
hermetic 使用的回放脚本给出的是精简回答。

## 已知局限

1. **不具区分度**（见上）。改进方向是提高单题难度，而非扩大题量。
2. **`tool_call_accuracy` 的含义比名称窄**：它统计的是工具类**判据**的通过率，
   而非独立的「工具调用正确性」度量。一个用例含多条工具判据时，全部通过才计 1。
3. **未使用 LLM-as-judge**。开放式回答依赖关键字匹配。引入 judge 需先解决
   judge 自身的可信度校验（与人工评分的校准），在 22 个客观用例的场景下收益不足。
4. **样本量小**。22 用例 × 5 次 = 110，百分比粒度为 1/110，
   小于 1% 的差异无统计意义，因此报告中同时标注样本量。
