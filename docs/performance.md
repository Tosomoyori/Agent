# 性能：实测数字与它的边界

「你的框架能扛多少并发」是校招面试里几乎必问的一题。没有数字的「性能很好」
是负分——它说明你没测过。这份文档给出**有边界、可复现**的数字。

复现方式：

```bash
uv run agentkit serve --port 8125 --db .agentkit/loadtest.db
uv run python scripts/loadtest.py --port 8125 --levels 1,5,10 --runs-per-level 8
```

每次请求是一个需要真实调用工具的任务（「列出当前目录的文件，然后告诉我一共有几项」），
走完整链路：建 run → SSE 订阅 → 引擎循环 → 工具执行 → 收尾。

---

## 结果（2026-10-05，`deepseek-flash`）

| 并发 | 成功/总数 | 失败率 | 墙钟 | 吞吐 | 总延迟 P50 | P95 | 最大 | **引擎耗时 P50** |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 8/8 | 0.0% | 15.4 s | 0.52 /s | 1954 ms | 2223 ms | 2290 ms | 1945 ms |
| 5 | 8/8 | 0.0% | 4.7 s | 1.70 /s | 1969 ms | 2532 ms | 2745 ms | 1945 ms |
| 10 | 8/8 | 0.0% | 2.2 s | 3.58 /s | 1818 ms | 2182 ms | 2233 ms | 1780 ms |

共 24 次真实调用，**零失败**。

---

## 三个能说明问题的观察

### 1. 延迟不随并发上升

P50 在并发 1 / 5 / 10 下分别是 1954 / 1969 / 1818 ms——**基本是一条平线**。

这一条比吞吐数字更有意义：它说明框架内部**没有排队或争用**。
如果事件分发、SQLite 写入、或 SSE 编码里有任何一处是串行的瓶颈，
并发一上去 P50 就会翘头。它没翘。

### 2. 框架自身的开销不到 1%

「总延迟」是脚本端测的墙钟时间，「引擎耗时」是 `RunCompleted` 事件里
引擎自己统计的那一段。两者的差 = HTTP 往返 + SSE 传输 + JSON 序列化。

并发 1 时：`1954 - 1945 = 9 ms`。

**也就是说这条链路上 99.5% 的时间是在等模型返回**，框架本身（内容块消息转换、
事件分发、工具执行、追踪记录、SSE 编码）加起来不到 10 毫秒。

这个数字要主动说出来，因为它同时说明了两件事：框架开销可以忽略，
**以及「总延迟 1.9 秒」这个数字不能拿来当成框架的性能**——那是模型的速度。

### 3. 吞吐不随并发线性增长

1 → 5 是 3.3 倍，5 → 10 只有 2.1 倍。原因有两个，都不在框架这边：

* **模型服务端的排队**。DeepSeek 的限流是**并发数**而非 RPM（超限返回 429），
  请求在服务端会排队；
* **压测脚本自己是单进程 asyncio**，10 个并发连接共享一个事件循环，
  解析 SSE 的开销也在里面。

要测出框架的真实上限，需要多进程压测客户端，并且把模型换成假的。
**这件事没做**——因为对一个作品集项目来说，「框架开销 < 1%」这个结论
已经足够说明问题，再往下测的是模型服务端和网络，不是我的代码。

## 这个数字的边界（必须说清楚）

| 维度 | 测到了 | 没测到 |
| --- | --- | --- |
| 并发 | 1 / 5 / 10 | 更高并发下的表现、429 限流的实际触发点 |
| 时长 | 单次压测约 22 秒 | 长时间运行（内存增长、SQLite 膨胀、连接泄漏） |
| 会话 | 每次请求独立 | 多轮会话下的上下文裁剪开销 |
| 工具 | 只读工具（`list_directory`） | `run_command` 的子进程开销与审批等待 |
| 部署 | 本机单实例 uvicorn | 多实例、容器、反向代理 |

**没有测长时间运行。** 这是一个真实的缺口：`RunManager` 有回收逻辑
（已结束且无订阅者的 run 会被清掉），SQLite 有 TTL 设计，
但这些**都没有在跑了几小时之后验证过**。想声称「可以长期运行」，
需要的是持续几小时的压测加内存曲线，那没做。

---

## 如果要往上压，先动哪里

按性价比排序：

1. **换掉压测客户端**——多进程 + 假模型，把模型服务端的影响排除，才能测到框架上限；
2. **给 SQLite 加异步写入队列**——现在每次 `record` 都走 `asyncio.to_thread`，
   会话多、写入频繁时线程池会成为瓶颈；
3. **`RunManager` 的事件缓冲带上限**——现在每个 run 的事件全留在内存里直到被回收，
   长会话（几百轮）会堆起来。给个环形缓冲或者落盘更稳；
4. **OTel 导出改批量**——现在 JSONL 是同步追加写，高频下会变成热点。

这四条都不是「现在很慢」，而是「并发再上一个量级时会先撞到的地方」。
