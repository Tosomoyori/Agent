# 评测：结果、以及过程中暴露的问题

## 最终数字

命令：

```bash
uv run agentkit eval eval_suites --mode live --trials 5 --concurrency 4
```

22 个用例 × 5 次 = **110 次真实调用**（模型 `deepseek-flash`）：

| 指标 | 值 |
| --- | --- |
| 任务成功率 (TSR) | 100% |
| pass@5 | 100% |
| pass^5 | 100% |
| 工具调用准确率 | 100% |
| 平均步数 | 2.95 |
| 平均工具调用数 | 3.06 |
| 延迟 P50 / P95 | 2932 ms / 4677 ms |
| 总成本 | 0.0888 CNY（110 次） |
| **每次成功成本** | **0.0008 CNY** |
| 总 token | 入 466,981 / 出 26,245 |

---

## 这个 100% 说明什么，不说明什么

**必须诚实：它说明套件不具区分度，而不说明 agent 完美。**

22 个用例对当前的前沿模型来说是偏容易的——它们考的是「会不会用工具读文件、
能不能递归计数、会不会被干扰项骗」。这些能力在 2026 年的模型上已经基本饱和。
一个所有用例都通过的基准，作为**回归基线**有价值（改动之后跑一遍，看有没有
退化），但作为**能力证明**没有价值。

所以这些数字正确的用法是：

* ✅ 「我建立了可复现的评测基线，110 次调用零失败，每次成功成本 0.0008 元」——
  这是工程能力的证明；
* ✅ 「P95 延迟 4.7 秒，主要花在模型推理上」——这是真实的性能画像；
* ❌ 「我的 agent 任务成功率 100%」——这句话不成立，它只对这套题成立。

要有区分度，需要更难的任务：多文件重构、需求有歧义需要澄清、长程规划
（10+ 步）、以及**该拒绝执行的请求**。

---

## 更重要的一件事：我的判据错了五次

这是这次评测里最有价值的产出，比上面那堆数字重要得多。

第一轮跑完是 `TSR 85%`。看失败明细，**六条失败全部是判据在惩罚正确的回答**：

| 用例 | 判据 | 模型实际做了什么 |
| --- | --- | --- |
| `locate_file_by_name` | 禁止答复里出现 `core.py` | 说「test_alpha.py、test_beta.py 匹配；core.py 不以 test_ 开头」——**正确** |
| `missing_file_handled_gracefully` | 禁止出现目录里那个文件的内容 | 说「nothere.txt 不存在，目录下只有 present.txt」——**正确** |
| `distractor_file` | 禁止出现候选版文件名 | 说「release-2.0.0.txt 是最高正式版；release-candidate-9.9.9.txt 是候选版不算」——**正确** |
| `cross_file_inconsistency` | 禁止出现一致的三个文件名 | 说「worker.conf 不一致，其余三个都是 8080」——**正确** |
| `large_file_needs_search` | 禁止出现 `E402` | 答的是 `E4021`，**子串命中** |
| `large_file_needs_search` | 禁止出现 `3` | 答的是 `13`，**子串命中** |

前四条是同一个错误的四种表现：**`answer_not_contains` 在检查措辞，不是在检查事实**。
后两条是它的机械版本：**字面子串匹配会误伤。**

### 教训

**能动用正面判据（必须出现某个关键事实）的，就别用负面判据。**

负面判据只在一种情况下成立：那个词**绝无可能**作为正确内容的一部分出现。
「不能出现 3」不满足这个条件（13 里有 3），「不能提到 core.py」也不满足
（说明它不匹配是正确行为）。

判断不了的时候，**去改问题本身，让它有可判定的答案**：不要问「哪个文件不一致」
（判据要解析散文），改问「那个不一致的 port 是多少」（答案唯一，判据是
`answer_contains: ["9090"]`）。

### 为什么 hermetic 模式没提前发现

因为 hermetic 模式用的是**我自己写的脚本**，脚本给的是精简回答（「worker.conf」），
而真实模型给的是解释性回答（「worker.conf 不一致，其余三个都是 8080」）。

这说明 hermetic 模式的定位要说清楚：**它验证的是框架自身的逻辑（工作区隔离、
聚合算法、判据的执行），不是判据的措辞是否合理。** 后者只能靠真跑一次来发现。

这个坑在设计里其实已经预见到了（`case.py` 的文档里写了「不检查措辞」），
但**写下原则和按原则写作是两回事**——判据是要一条条写出来的，写的时候
很自然地就滑向了「列出不该出现的词」。所以那条警告现在直接放在
`CheckSpec.contains` 的字段文档里，写在会看到它的地方。

## 三层测试的分工

这个项目里有三种「测试」，各自答不同的问题，不该混为一谈：

| 层 | 命令 | 答什么问题 | 成本 |
| --- | --- | --- | --- |
| 单元测试 | `uv run pytest` | 每个组件的逻辑对不对 | 0 |
| 评测（hermetic） | `agentkit eval ... --mode hermetic` | **评测框架自己**对不对 | 0 |
| 评测（live） | `agentkit eval ... --mode live` | agent 在真实任务上的表现 | 真实 API 费用 |

第一层和第二层的区别容易被忽略：单测测的是 `run_checks` 这个函数的行为，
hermetic 评测测的是**整套用例 + 判据 + 工作区隔离**跑起来是否自洽。
一个判据写错的用例，单测全绿也发现不了。

## 已知的局限

1. **不具区分度**（见上）。要改进就得加更难的用例，而不是加更多同类用例。
2. **`tool_call_accuracy` 的含义比名字窄**。它统计的是工具类**判据**的通过率，
   不是「工具调用是否正确」的独立度量——一个用例里有多条工具判据时，
   全对才贡献 1。名字保留是为了好读，但知道这一点很重要。
3. **没有 LLM-as-judge**。开放式回答的评判目前靠关键字。引入 judge 需要
   先解决「怎么验证 judge 本身可信」（与人工评分的校准），那是另一个课题，
   在 22 个客观用例的场景下不值得。
4. **样本量小**。22 个用例、5 次试验，报告里的百分比粒度只到 1/110。
   任何小于 1% 的差异都没有意义——所以报告里同时给出样本量。
