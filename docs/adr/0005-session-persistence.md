# ADR 0005：会话持久化用 SQLite 自造，不委托 Temporal/DBOS

**状态**：已采纳

## 问题

对话历史怎么存？中断的 run 怎么恢复？

## 选项

**A. 委托给持久化执行引擎。** PydanticAI 明确采取这条路线：**不自造 checkpointer**，
把持久化交给 Temporal / DBOS / Prefect / Restate。

**B. 自造。** SQLite 存消息与事件，自己处理恢复语义。

## 决定

选 **B**。但**只做了会话级持久化，没做 run 级的中断恢复**（见下方「代价」）。

## 理由

A 的设计理由成立——对**分布式、长周期**的工作流（跑几小时、跨多台机器、
外部副作用需要 exactly-once），自己实现持久化执行几乎必然出错，
而 Temporal 那类系统是为此专门造的。

但这个项目不满足那些前提：

* run 是**秒级**的，不需要跨机器；
* 部署形态是单进程 CLI 或单实例服务；
* 引入 Temporal 意味着**要跑一个服务**——而"clone 下来 `uv sync` 就能跑"
  是这个作品集项目的核心卖点之一。

选 B 之后还有一个额外的好处：**恢复语义是我自己定义的，我能讲清楚它**。
用 Temporal 的话，「进程崩了恢复到哪一步」这个问题会变成「Temporal 是怎么做的」，
而我说不清。

## 代价（以及没做到的部分）

* **必须自己解决副作用幂等。** 重放时不能重复执行 `write_file` 或 `run_command`。
  当前的设计是给工具打 `idempotent` 标记（[`tools/base.py`](../../src/agentkit/tools/base.py)
  的 `ToolSpec.idempotent`），`run_command` 标了 `False`——但**幂等键机制本身
  没有实现**，这是已知缺口。
* **事件日志的版本兼容**要自己管。消息结构变了，旧数据要能读出来。
  目前靠 pydantic 的默认值和对未知字段的宽容。
* **run 级中断恢复没有做。** 现在有的是：会话级消息持久化（下一轮能看到历史）、
  事件流全程可观测（[`runtime/bus.py`](../../src/agentkit/runtime/bus.py)）、
  以及**落盘前的配对不变量校验**——取消或出错时消息序列可能残缺
  （assistant 的 `tool_use` 还没等到 `tool_result`），**这种轮次不写入**，
  否则下一轮一开场就会被 API 拒绝。

  做完整的 run 级恢复，需要的是 append-only 的事件日志 + 重放 + 副作用幂等键。
  路径清楚，但那是另一个工作单元的体量。

* **存储层要自己处理并发。** 已实现的部分：SQLite 连接用
  `check_same_thread=False` 打开并配一把 `RLock` 串行化访问——
  打开那个开关不是"允许跨线程共享"，而是"关掉检查，安全责任转移给调用方"。

## 什么情况下该推翻这个决定

出现下列任一情况就应该换成 A：需要跑小时级的工作流、需要跨机器恢复、
或者副作用的 exactly-once 成为硬需求。
