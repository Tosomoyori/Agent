# ADR 0008：评测主指标用 pass^k 和状态判据

**状态**：已采纳

## 问题一：评什么？

**A. 拿最终答复跟参考答案做字符串比对。**
**B. 检查执行后的**状态**（文件在不在、内容对不对）+ 答复里的关键事实。**

### 决定

选 **B**。

### 理由

A 有两个致命问题：

1. **措辞不同就算错。**「有 43 个文件」和「src/agentkit 下共有 43 个 .py 文件」
   是同一个答案；
2. **过程对、结果错。** 模型可能说「我已经把文件写好了」而实际什么都没写。
   比对答复永远发现不了。

这个思路来自 τ-bench：**按最终数据库状态评分，而不是按 transcript 评分**。

## 问题二：报哪个成功率？

设跑了 `n` 个用例、每个重复 `k` 次：

| 指标 | 定义 | 衡量 |
| --- | --- | --- |
| TSR | 全部 `n×k` 次里通过的比例 | 平均表现 |
| pass@k | k 次里**至少成功一次**的用例比例 | 潜力 |
| **pass^k** | k 次**全部成功**的用例比例 | **可靠性** |

### 决定

**三个都报，但主指标是 pass^k**，并在报告里断言
`pass^k ≤ TSR ≤ pass@k` 恒成立——免得只挑好看的那个报。

### 理由

一个 `pass@5 = 1.0` 但 `pass^5 = 0.4` 的 agent，意味着它能做对，但五次里只有
四成能五次全对——**用户每次调用都在赌**。τ-bench 的原始结果里 retail 场景
pass^8 不到 25%，这个数字比 TSR 有信息量得多。

## 代价

* **pass^k 要跑 k 次，贵且慢**。所以评测分两层：
  * **hermetic** —— 用假模型回放，零成本、确定、可进 CI，验证**评测框架自己**；
  * **live** —— 真实调用，测 agent 的真实能力。
* **状态判据要给每个用例写检查器**，比字符串比对麻烦得多；
* 判据本身会成为错误来源——具体约束见 [docs/evaluation.md](../evaluation.md)
  的「判据设计约束」一节。

## 副作用：成本必须和成功率并列

报告里同时给「每次成功成本」，而不是只给总花费——总花费没有可比性。

查不到价格时返回 `None`，**不填 0 冒充**。同样地，只要有任意一次运行没拿到价格，
总成本就返回 `None`：那种「3 次里 2 次查到价格」的数字看起来精确，实际少算了三分之一。

## 未做的：LLM-as-judge

开放式回答的评判目前靠关键字。引入 judge 需要先解决「怎么验证 judge 本身可信」
（与人工评分的校准、偏见检测），那是另一个课题。在 22 个客观用例的场景下不值得。

## 未做的：CI 门禁

框架类和平台类评测工具（DeepEval / promptfoo / Braintrust）的价值之一是能在 PR 上
**阻断**低分变更。项目目前没有 CI，所以这条没做。要做的话，
`agentkit eval --mode hermetic` 已经可以无条件进 CI（零成本、零外部依赖）。
