# ADR 0007：重试只发生在第一个 chunk 之前

**状态**：已采纳

## 问题

调用 LLM 会失败（限流、超时、5xx）。重试策略怎么定？

## 决定

三条规则：

### 一、只重试标记为可重试的错误

| 该重试 | 不该重试 |
| --- | --- |
| 429 限流 | 400 请求非法 |
| 5xx 服务端错误 | 401 / 403 认证失败 |
| 408 超时、网络抖动 | 404 |

判定依据是 [`core/errors.py`](../../src/agentkit/core/errors.py) 里的 `retryable`
标记，**不做类型名猜测**：猜错会把一次性的错误变成重复扣费。

### 二、必须关掉 SDK 自带的重试

适配器构造 `AsyncOpenAI` 时固定传 `max_retries=0`。

两边都开的话实际重试次数是**相乘**的：SDK 的 3 次 × 自定义的 3 次 = 9 次。
遇到限流时这个数字会把配额耗光，而且从日志上完全看不出来——
每一层都以为自己只重试了 3 次。

### 三、流式请求只在第一个 chunk 之前可以重试

```python
async for item in make_stream():
    emitted = True
    yield item
...
except AgentKitError:
    if emitted:
        raise   # 已经吐过内容，重试会造成重复输出与重复计费
```

**一旦有 token 吐给调用方，中途断掉就属于终态。** 重来一次会有两个后果：
调用方收到重复内容；那部分输入 token 已经计过费了。

这不是保守，是正确性：**调用方已经看到的东西没法撤回**，假装没发生过只会更糟。
第一条规则（只重试可重试的错误）在这一条面前要退让。

## 退避用 full jitter

`delay = random(0, min(cap, base * 2^(attempt-1)))`

不用固定的指数退避：多个客户端同时被限流时，固定退避会让它们在**同一时刻**
一起重试，形成二次冲击。随机化把重试时刻摊开。

## 尊重 Retry-After

服务端明确说了等多久就听它的——但要设上限（60 秒），
不该被一个离谱的值把进程挂住。

这里有个实现上的坑：错误映射会把原始异常包一层，而 `Retry-After` 在响应头上，
包完就丢了。所以 `map_openai_error` 会**主动把响应头里的值提取出来**，
存到自己的错误对象的 `retry_after` 字段上，让重试层能统一读到，
不必去翻各家 SDK 的原始异常。

同时认两种头：`retry-after-ms`（毫秒，较新的标准）优先，`retry-after` 次之。
HTTP 日期格式的不解析——解析不了就当没有，不猜。

## 未做的：熔断与降级

生产系统通常还会配熔断器（连续失败就停止调用）和 fallback 链
（主模型 → 备用模型 → 缓存 → 静态回复）。本项目的规模不需要，
而且没有真实的故障注入测试，加了也只是摆设。

## 代价

* 要维护一张错误码 → 是否重试的映射表；
* 有副作用的工具调用在重试时需要幂等键，**这一条还没实现**
  （见 [ADR 0005](0005-session-persistence.md) 的「代价」）；
* DeepSeek 限的是**并发数**而不是 RPM，所以高并发场景需要信号量而不只是退避。
  当前通过评测运行器的并发上限（默认 3）间接控制。
